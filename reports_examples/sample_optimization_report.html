IDX001 — Covering (INCLUDE) on customers (Medium confidence)

Related Condition: c.country = 'India'

CREATE INDEX idx_customers_country_cov ON customers(country) INCLUDE (customer_id, email, segment);

Why it helps: Includes projected columns (customer_id, email, segment) as non-key leaf payloads, enabling an Index-Only Scan without visiting the main heap table (once visibility map pages are clean).

Existing Index Check: No existing index on 'customers' has 'country' as leading key.

Write & Storage Overhead: Larger index leaf pages than a plain single-column index; updates to INCLUDE columns also update the index.

When It May Not Help: If the table receives heavy UPDATE traffic on the INCLUDE columns, or if queries frequently change projected columns.

IDX002 — Single-Column B-tree on customers (High confidence)

Related Condition: c.country = 'India'

CREATE INDEX idx_customers_country ON customers(country);

Why it helps: Allows PostgreSQL to jump directly to matching 'customers.country' entries via Index Scan / Bitmap Index Scan instead of scanning the entire table sequentially.

Existing Index Check: No existing index on 'customers' leads with 'country'.

Write & Storage Overhead: Increases INSERT/DELETE time slightly and updates on 'country'; adds B-tree disk footprint.

When It May Not Help: Not beneficial if the query returns a large fraction (>20–30%) of table rows, if the table is small, or if predicates wrap the column in non-sargable functions.

IDX003 — Composite B-tree on orders (High confidence)

Related Condition: o.customer_id = c.customer_id; o.status = 'delivered'

CREATE INDEX idx_orders_customer_id_status ON orders(customer_id, status);

Why it helps: Follows the Equality-Sort-Range (ESR) B-tree ordering rule: equality keys narrow directly to a contiguous slice while trailing range/sort columns avoid extra filtering or Sort steps.

Existing Index Check: No existing index on 'orders' starts with (customer_id, status).

Write & Storage Overhead: Adds B-tree maintenance cost on INSERT and on UPDATEs modifying any indexed column; wider keys consume slightly more disk/buffer space than single-column indexes.

When It May Not Help: Ineffective if the leading equality column has very low selectivity (matching >25% of rows) or if queries omit the leading column.
